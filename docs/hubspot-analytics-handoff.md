## Context — read this first

**The site.** Static HTML, deployed to Cloudflare Pages. Local repo at `ABM Website`.
Pages are partly hand-maintained and partly generated by Python scripts
(`build_pages.py`, `generate_pages.py`). Python 3.12 required.

**How forms currently reach HubSpot.** The site does **not** use embedded HubSpot form
iframes, and does **not** use the HubSpot CRM API. It uses the **HubSpot Forms API**:

- `scripts/hubspot-form.js` wires any `<form data-hs-form="FORM_GUID">` on the page to
  `https://api.hsforms.com/submissions/v3/integration/submit/14501596/{formGuid}`
- Field `name` attributes must match HubSpot internal property names
  (`firstname`, `lastname`, `email`, `phone`, `company`, `annualrevenue`,
  `budget_allocation_per_month_contact`)
- The script reads the `hubspotutk` cookie and sends it as `context.hutk`

**Do not migrate these forms to the HubSpot CRM API.** This was evaluated and rejected.
The Forms API passes `hutk`, which ties each submission to the visitor's full analytics
session — original traffic source, pages viewed, campaign attribution. It also records a
form-submission event on the contact timeline and fires form-submission-based workflows.
The CRM API (`/crm/v3/objects/contacts`) does none of that, requires a backend proxy to
hold a secret, and adds failure surface. For an agency whose reporting depends on
attribution, switching would be a net downgrade.

If server-side submission is ever wanted, proxy the **Forms API** through a Cloudflare
Worker (forwarding the `hutk` read client-side). That does not require the CRM API.

## Task 1 — Reconcile `build_pages.py` with the live `contact.html` ⚠️ DO FIRST

**Why.** `build_pages.py` generates `contact.html` (see the `page("contact.html", ...)`
call around line 269, fed by `contact_body`). That generator is **stale**. It still emits:

- a placeholder div: `<div id="hubspot-contact-form" class="hubspot-placeholder">` with the
  text "HubSpot contact form mounts here"
- a long HTML comment (~lines 215–221) with `hbspt.forms.create({...})` embed instructions
- a commented-out Formspree fallback form

The live `contact.html` on disk has none of that — it has the real working custom form with
`data-hs-form="ceab7d85-..."`. The GUID `ceab7d85` **does not appear anywhere in

This means **running `build_pages.py` will overwrite `contact.html` and delete the working
contact form**, replacing it with a placeholder. The contact form would silently break, and
lead capture would stop. This is a live landmine sitting in the repo.

**What needs to happen.**

   `contact_body` string in `build_pages.py`, so the generator produces what is actually
   live. Include the `<script src="scripts/hubspot-form.js" defer></script>` tag.
2. Delete the stale placeholder div, the `hbspt.forms.create` instruction comment, and the
   Formspree fallback block from `build_pages.py`.
3. Delete the same stale comment block from the live `contact.html` (it is inside an HTML
   comment, so it is invisible to users, but it is actively misleading to anyone reading
   the file — it makes it look like the page is waiting for a HubSpot embed).
4. Run `build_pages.py` and diff the output against the committed `contact.html` to confirm
   the generator now reproduces the live page byte-for-byte before committing.

## Task 2 — Delete the unused HubSpot service key

**Why.** A HubSpot **Service Key** named `ABM Website Contact Forms` (id `51666999`, scope
`crm.objects.contacts.write`) was created on 2026-09-02, on the assumption that the site
needed the CRM API for form intake. That turned out to be wrong — the Forms API path
described above was already in place and is the better approach. The key is unused.

An unused write-scoped credential is pure downside: it is one more secret that can leak,
and it grants write access to the contacts database with nothing depending on it.

**What needs to happen.** In HubSpot: **Settings → Development → Keys → Service Keys →
`ABM Website Contact Forms` → Delete**. Deletion is permanent and cannot be undone; that is
fine here because nothing references the key. The token was never copied into any file,
repo, or environment variable, so there is nothing else to clean up.

Note: HubSpot Service Keys are currently labeled **Beta**, and are HubSpot's recommended
replacement for legacy private apps (which no longer receive new scopes or platform
improvements). If server-side HubSpot work is ever needed later, create a fresh key then,
scoped to exactly what that job requires.

## Task 4 — Fire conversion events when a form is submitted ⭐ HIGHEST VALUE

**Why.** The form submits to HubSpot successfully and then does nothing else. The success
handler in `scripts/hubspot-form.js` shows a thank-you message and resets the form. There is
**no `dataLayer.push`, no `gtag` event, no conversion signal of any kind** — confirmed by
grep across `scripts/hubspot-form.js` and `scripts/content-gate.js`.

GA4 (`scripts/ga4.js`) is loaded on `contact.html`, so pageviews are recorded. But a lead
submission is not a measurable event anywhere.

Consequences right now:

- No GA4 conversion event for lead submissions
- Google Ads has no conversion to optimize bidding against — Smart Bidding is flying blind
- No way to measure contact-page conversion rate, or compare traffic sources by lead quality
- The gated-resource downloads (`content-gate.js`) are equally uninstrumented

This is a bigger hole than anything else in this document. The site is running paid traffic
to a contact page whose conversion is not instrumented.

**What needs to happen.**

1. In `scripts/hubspot-form.js`, in the `.then()` success branch (after the `res.ok` check
   passes, alongside `setStatus(form, message)`), push a GA4 event:

   ```js
   window.dataLayer = window.dataLayer || [];
   window.dataLayer.push({
     event: 'lead_form_submit',
     form_id: formId,
     form_name: form.getAttribute('data-hs-form-name') || 'contact',
     page_path: window.location.pathname
   });
   ```

2. Do the same in `scripts/content-gate.js` on successful unlock, with a distinct event name
   (e.g. `gated_content_unlock`) plus the resource slug, so guide downloads and contact
   requests are measured separately. They are different intent levels and should not be one
   conversion.
3. Only fire on genuine success — not in the `.catch()` branch, and not on validation
   failure. A conversion event that fires on a failed submit poisons the data.
4. In GTM (`GTM-NN575G4`): create a Custom Event trigger for `lead_form_submit`, and a GA4
   Event tag that fires on it. Repeat for `gated_content_unlock`.
5. In GA4: mark `lead_form_submit` as a key event (conversion).
6. In Google Ads: import the GA4 key event as a conversion action. Give it a value if
   average lead value is known; otherwise leave unvalued and optimize for volume initially.

**Verification:** submit a real test form, confirm the event appears in GA4 DebugView and in
GTM Preview mode, then confirm the contact was created in HubSpot. Check that a *failed*
submit fires nothing.

## Task 5 — Deploy GTM sitewide

**Why.** The GTM container `GTM-NN575G4` was added to `index.html` only (head script + body
noscript), in August 2026, and was never deployed or rolled out to the other pages. Grep
confirms `GTM-NN575G4` appears in exactly one file. There are 33 live HTML pages.

Task 4 depends on this: the `dataLayer` events will fire on `contact.html` and the resource
pages, but with no GTM container loaded on those pages, nothing will be listening. **Task 4
is inert until this is done.**

**What needs to happen.**

1. Decide where the container tag belongs. Because pages are generated, it must go into the
   generators, not into the output HTML — otherwise the next build wipes it. Note
   `generate_pages.py` line ~39 already centralizes the GA4 tag injection
   (`<script src="{rel}scripts/ga4.js" async></script>`); the GTM tag should follow the same
   pattern, in the same place.
2. `build_pages.py` has its own head/body template (around lines 28 and 94) — the GTM head
   script and body noscript need adding there too.
3. Rebuild all pages and confirm `GTM-NN575G4` now appears in all 33 live pages.
4. Deploy to Cloudflare Pages, then verify on the live site (not just locally) — the August
   note records that the live site was serving a cached version without GTM, so confirm the
   deploy actually propagated.

**Verification:** GTM Preview mode connects successfully on `/contact.html` and on a
resource page, not just the homepage.
